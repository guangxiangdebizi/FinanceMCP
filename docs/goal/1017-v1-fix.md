# FinanceMCP AShare：下一轮正确性修复与正式验收任务

## 背景

仓库：https://github.com/jingchangshi/FinanceMCP

目标分支：`ashare-daily`

审阅基线 commit：`371c2c47046290653695827fbc2628aa3ae7a187`

当前 FinanceMCP AShare 已实现 Tushare 数据回填、SQLite、市场分析、技术信号、股票池、五个只读 MCP Tools、HTTPS 入口和 systemd timer。

当前已有的构建、真实历史数据、MCP 公网自测结果必须保留。

本轮不是重新开发系统，也不是优化选股收益，而是修复独立审阅发现的正确性问题，保证 2026-10-19 开始的真实交易日验收能够可信进行。

## 一、P0 必须完成

### P0-1：当天核心数据强制复查

检查 `src/ashare/ingest.ts` 中 `syncedOk()` 跳过数据下载的问题。

当前 18:40 数据被标记 `ok` 后，21:10 的执行可能不再向 Tushare 获取更新数据。

修复要求：

- 当日再次执行 daily 时，必须实际重新检查当日核心行情。
- 不重新下载所有历史日期；只刷新必要的最近交易日。
- 数据发生修订时正确替换旧数据，而不只是追加缺少的行。
- 同一交易日多次执行不产生重复数据或异常状态。
- 增加模拟首次返回不完整、第二次补齐的回归测试。

### P0-2：正式运行和历史回放隔离

检查 `replay`、`report --date`、`resetWatchlistFrom()` 和 `generateReport()` 对持久化股票池的修改。

修复要求：

- 历史回放不得覆盖已经封存的正式 live 股票池。
- 历史研究使用隔离数据库或等效的最小隔离方式。
- 对已有真实日期执行手动报告生成，不得破坏后续日期的股票池连续性。
- 增加测试：创建若干 live 日期后执行历史 replay，验证 live 数据和报告未改变。
- 不引入新的数据库服务或通用事件溯源框架。

### P0-3：历史效果评价严格遵守 as-of

检查 `evidence.ts` 的 `evaluateWatchlist()`。

修复要求：

- 统计评价窗口必须截至显式 `end`。
- 只有在 `end` 之前已经完整实现的未来 N 日收益才能纳入统计。
- 加入 end 之后的新行情，不应改变原先的 as-of 历史报告。
- 历史重放不得把未来计算的信号证据分类标注为历史当时已知。
- 用测试证明这些约束，而不是只更新文档。

## 二、P1 小范围修复

1. 检查 `latestReportMeta`，确保最新市场报告按交易日排序，历史 replay 不得取代正式最近日报。
2. 修正连续三日验收中 `READY` 与 `DEGRADED` 的混淆，明确对应通过条件。
3. 复权因子缺失的股票不得悄悄退化为混合价格序列并继续输出确定性的技术信号。
4. 将 `evidence_supported` 的展示描述限定为样本内方向性证据；说明收益窗口重叠和多重检验的限制。暂不开发新的复杂统计引擎。
5. 检查现有无认证 MCP 部署的只读边界、请求大小、限流和数据访问范围。不要为了本任务引入 OAuth 平台，但必须记录匿名开放的实际风险。
6. 检查 systemd user timer 是否能在用户注销和 VPS 重启后保持有效，Docker 未就绪时是否能正确报错。

## 三、验收要求

执行完整 `npm test`、TypeScript 构建、MCP 工具回归测试。

使用已有真实历史缓存完成：

- 10 月 16 日日报读取。
- 同日重复数据同步。
- 新增数据和修订数据测试。
- 历史回放与 live 数据隔离测试。
- as-of 不变性测试。
- 五个 MCP Tool 接口验证。
- NOT_READY / DEGRADED / READY 状态检查。
- 关键文件的磁盘持久化验证。

优先通过自动化单测和已有真实数据证明修复正确，不为验收重复执行数百万行的完整数据回填。

## 四、真实交易日验收

2026-10-19、2026-10-20、2026-10-21 分别检查真实 systemd 执行记录。

每个日期记录：

- 两次计划运行是否实际触发。
- 每次 Tushare 同步是否成功。
- 是否真正复查当日行情。
- 最终报告状态与生成时间。
- 股票池数量及增减是否连续。
- MCP 返回的报告 ID 是否与数据库一致。
- ChatGPT 手动和定时任务调用证据（用户侧验证）。
- 是否存在数据缺失、容器重启、存储或权限错误。

只有日期真实发生并产生证据，才可将对应验收项改为 PASS。禁止回填或伪造未来日期结果。

不能执行的用户账号侧检查保留为 PENDING，并提供明确的手动测试指令。

## 五、边界

- 继续使用 FinanceMCP + TypeScript + SQLite + systemd。
- 不引入 TactiCore 或 Python。
- 不建设新的量化回测引擎、Agent 平台或数据基础设施。
- 不调整 `score-1.0.0` 的评分权重来追求近期历史收益。
- 不删除或改写现有负面研究结果。
- 不将样本内信号显著性称为生产策略有效性。
- 不为了等待未来交易日而保持 Coding Agent 会话持续空转。

## 六、交付

提交经过测试的最小修复，更新 `docs/ashare-acceptance.md`，写清每项问题的根因、修改文件、测试命令、证据及剩余风险。

将代码推送到新的修复分支，提供提交 SHA 供独立复核。

完成当前可以完成的全部工作后正常结束会话，未来三日的定时验收由 VPS 系统调度和正式验收命令承担，而不是依赖 Agent 会话存活。
