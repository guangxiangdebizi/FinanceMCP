## 二、P0：保护正式数据库

审阅 `src/ashare/snapshot.ts` 的：

- `openSnapshotDb()`
- `runResearchSnapshot()`
- `runResearchEvaluate()`

目前研究库与正式库仅通过路径字符串比较，不能识别指向同一个文件的路径别名。

要求：

- 在打开研究库可写连接前完成路径检查。
- 对存在的文件使用规范化路径和文件身份检查。
- 识别符号链接及硬链接。
- 当研究库与正式库指向同一个 SQLite 文件时拒绝执行。
- 两个研究命令均使用同一检查逻辑。
- 对默认研究库路径保持原有行为。

新增反例：使用正式数据库的相对路径、符号链接、硬链接作为 `--db` 参数。命令必须拒绝，并证明正式库内容未修改。

只实现必要的路径安全检查，不建立通用文件权限系统。

## 三、P0：冻结原始 V2 股票池状态链

当前 `--revise` 会更新 `pool_state`，后续日期可能使用修订后的状态。

修改规则：

- `ORIGINAL` 快照进入正式前瞻研究状态链。
- `REVISED` 快照只追加修订证据。
- 修订不得覆盖原始日期对应的 V2 状态。
- 后续日期默认继承前一交易日的原始 V2 状态。
- 每份快照应保存实际继承的前一快照 ID。
- 同一天重复运行保持幂等。

如果缺少应有的前一交易日原始快照，不得悄悄使用更早日期继续并宣称“逐日连续”。

返回明确的缺口状态，允许后续按顺序补齐。

反例必须覆盖：

1. 先保存 T、T+1 两个交易日的原始快照。
2. 修订 T 的快照。
3. 验证 T 的原始状态未变。
4. 验证 T+1 继承的状态未变。
5. 验证再次计算后续日期时不会意外继承修订状态。
6. 缺少中间交易日时不生成虚假的连续状态。

不需要引入事件溯源框架或第二套数据库。

## 四、P1：区分前瞻与历史回补

当前 `ORIGINAL` 仅表示第一次存储。

增加独立的观察时间属性，至少区分：

- `PROSPECTIVE`：在规则冻结后，依据当时已发布的数据及时创建的研究观察。
- `BACKFILLED`：事后补充的历史研究快照。
- `REVISED`：已有快照的修订身份，不替代观察时间属性。

规则应明确记录：

- 交易日。
- 正式报告生成时间。
- 快照创建时间。
- 策略版本的冻结起点。
- 数据截止日。
- 数据质量。
- 是否晚于允许的前瞻记录窗口。

真正前瞻研究起点为 2026-10-19。

对于 2026-10-16 的功能验证快照，应保留其历史研究价值，但不能计入 2026-10-19 开始的前瞻统计。

不要依赖文件名判断前瞻属性，也不要允许事后修改标记使历史结果变成前瞻证据。

## 五、P1：公平的 V1/V2 前瞻比较

当前 V1 正式股票池已经积累历史状态，V2 首次快照则从空池初始化。

这一差异会影响股票池成员比较。

为从 2026-10-19 开始的正式前瞻对照实验建立相同起点：

- 使用 2026-10-16 最后一个正式 V1 股票池作为两版的共同初始状态。
- 保留成员的入池日期。
- 从 2026-10-19 起，分别使用 V1/V2 评分规则更新成员。
- V1 的实际结果仍以正式发布的 `watchlist` 为准。
- V2 在独立研究库中推进。
- 初始状态仅设置一次，并保存来源报告 ID、日期和成员摘要。
- 后续两版的成员差异才能归因于评分及由评分产生的独立状态演化。

对这一方案先建立确定性验证：以共同初始状态和 V1 评分运行，应与正式 V1 的下一交易日股票池一致。

如果验证发现已有正式运行状态与这一设计不兼容，保留现有历史研究结果，明确说明差异，不得强行修改正式股票池。

## 六、P1：修正生产调度核验范围

检查 `deploy/ashare/verify-production-untouched.mjs`。

当前脚本使用 `systemctl`，可能漏掉 `systemctl --user` 下的实际 timer。

应分别核查：

- 实际部署主机与执行用户。
- systemd 用户级 timer。
- systemd 系统级 timer。
- timer 是否启用。
- 下次触发时间。
- timer 对应的 service。
- service 实际调用的工作目录和脚本路径。
- Docker 容器状态及镜像版本。

不要因为系统级 timer 不存在就宣称不存在任何定时任务。

不修改原有调度时间或通知设置。
