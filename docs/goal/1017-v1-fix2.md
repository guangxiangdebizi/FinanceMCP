## 一、P0：手动报告必须与正式数据隔离

当前 `src/ashare/commands.ts` 中：

`report --date` 仅在指定日期早于最新 live 日期时才进入 research.sqlite。

如果 `date == lastLiveDate`，会在正式数据库调用 `generateReport()`，可能改写正式 watchlist、stock_score、latest.json，并使 MCP 返回手动报告而不是正式 live 报告。

### 修复要求

1. `report --date` 默认始终使用 research.sqlite。
2. `replay` 继续始终使用 research.sqlite。
3. 只有正式 `daily` 流水线可以生成新的 live 报告及其持久化股票池状态。
4. 当前日期等于最新 live 日期时执行 `report --date`，不得修改正式状态。
5. 研究报告输出到独立 research 路径，不覆盖正式 JSON 快照。
6. `latestReportMeta()` 在同一交易日优先选择正式 live 报告，而不是生成时间更晚的 manual/replay 报告。兼顾旧数据库中已经存在的 manual 记录。
7. 不引入新的状态管理服务或事件系统。

### 必须新增测试

- 最新 live 日期为 20261016，执行 `report --date 20261016`，确认结果进入 research。
- 对比命令执行前后正式 watchlist、watchlist_change、stock_score、report 和 latest.json，确认完全一致。
- 验证 MCP 仍然返回原 live report_id。
- 对更早日期和研究库中尚未生成的日期执行报告命令，不污染 live。
- 下一真实交易日的股票池能正常延续。

## 二、P0：区分缓存完整性与最新上游刷新状态

当前 `src/ashare/ingest.ts` 的同步状态主要根据写入后的 SQLite 行数判断。

存在如下问题：

第一次同步获取 5500 条记录，第二次由于上游异常只返回 3000 条。系统保留第一次的数据是正确的，但不能仅因为缓存仍有 5500 条就认为第二次刷新成功。

### 修复要求

明确区分以下两种状态：

- `cache_quality`：本地持久化数据是否满足质量门槛。
- `refresh_status`：本次实际 Tushare 请求是否返回完整、可信的数据。

保留当前 `READY / DEGRADED / NOT_READY` 的对外报告状态，不需要增加复杂状态机。

推荐最小方案：

1. 继续使用已有 `sync_log` 和 `sync_history`。
2. 同步结果中明确记录本次获取行数、原有行数、同步后行数、刷新是否完整及采取的写入方式。
3. 如果刷新结果明显短缺：
   - 不删除此前完整数据。
   - 若已有完整缓存，优先保留原有完整快照，避免把部分更新的数据混入其中。
   - 将本次刷新标记为 `REFRESH_INCOMPLETE`，不得将其标为刷新成功。
4. 如果此前缓存也不完整，可按现有规则合并有效数据，但仍需保留本次刷新不完整的标记。
5. 如果 Tushare 请求报错，记录失败信息，不能把失败记为成功。
6. 数据缓存满足要求、但最新一次刷新不完整时，最终日报不得标记为无异常的 READY。可使用 DEGRADED 并说明继续使用了上一次有效快照。
7. 如果缓存本身也不满足核心质量门槛，仍返回 NOT_READY。
8. 下一次成功刷新后，刷新异常应能正常解除。

确保 `ashare_data_status` 和 `ashare_daily_report` 能反映最新刷新异常，而不是只显示旧缓存的完整性。

不要为此引入单独消息队列、状态数据库或任务管理框架。

### 必须新增测试

A. 第一次 5500 条，第二次 3000 条：

- 数据不丢失。
- 第二次不被记录为成功刷新。
- 报告明确体现本次刷新异常。
- 不错误发布无异常 READY。

B. 第一次 3000 条，第二次 5500 条：

- 缓存成功补齐。
- 报告恢复 READY。

C. 第一次 5500 条，第二次 5490 条，且数据源确实撤回部分记录：

- 符合合理完整性门槛时，允许原子替换。
- 被撤回的记录不残留。

D. Tushare 请求抛出异常：

- 保留既有完整数据。
- 留下失败证据。
- 不伪装成成功获取最新数据。

E. 连续运行：

- 第一次刷新失败、下一次恢复成功后，状态应自动恢复。
- 不出现重复数据或错误股票池状态。

## 三、P1：澄清连续三日验收证据

当前 `acceptance.ts` 已要求每天两个 live 报告和两次 Tushare 获取记录。

但数据库中的两次执行记录本身不能证明它们由 systemd timer 触发。

要求：

1. 保留现有 acceptance 命令。
2. 检查两次刷新记录确实为有效请求，不把两次失败或不完整请求都计为通过。
3. 在文档中明确区分流水线执行证据与 systemd 调度证据。
4. 使用 systemd journal 的实际启动记录核对计划运行时间。
5. 不要求 acceptance CLI 自行解析宿主机 journal；允许通过独立日志核验完成调度验收。
6. 保持 DEGRADED 的验收规则不变：只有明确传入 `--allow-degraded` 才可放宽，且必须报告 `PASS_DEGRADED`。

真实交易日验收仍为 2026-10-19、20、21，禁止提前填写未来执行结果。
