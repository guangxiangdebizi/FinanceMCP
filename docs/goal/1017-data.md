## 0. 任务定位

仓库：https://github.com/jingchangshi/FinanceMCP

工作基线：`ashare-v1-fix2`

`docs/ashare-data-research-architecture.md`

架构文档已通过 PR #1 合入 main：

本轮不等待这些日期，也不提前执行或伪造三日验收。

## 一、核心目标

将 FinanceMCP 中现有的 A 股数据采集、存储和访问能力完善为独立的数据服务模块。

该模块向两个消费者提供一致的数据：

1. Oracle VPS 上的确定性量化分析引擎。
2. 通过 MCP 访问数据的 ChatGPT 研究层。

本轮目标不是提高股票池历史收益，而是确保数据完整、正确、可追溯、可按历史时点查询，并具备稳定的结构化访问接口。

执行完整开发流程：源码审阅 → 问题识别 → 修复实现 → 新接口开发 → 测试 → 真实缓存验证 → 文档更新 → 部署核验 → 提交。

不要只完成第一步或仅输出建议。

## 二、严格的模块边界

### 数据获取模块负责

- 多数据源获取与增量更新。
- 交易日历和股票基础信息。
- 日线、指数、成交量、估值及复权因子。
- 财务指标与公告日期。
- 数据清洗、存储及质量检查。
- 历史数据缺口检查和补齐。
- 数据来源、同步时间及异常记录。
- 按股票、日期、数据集提供只读结构化查询。

### 分析引擎负责

- MA、RSI、MACD、CCI、BOLL 等技术指标。
- 技术形态与量价信号。
- 市场状态和行业强度计算。
- 股票评分。
- 动态股票池维护。
- 信号有效性统计和历史回测。

### ChatGPT 负责

- 分解研究问题。
- 按需调用 MCP 获取真实数据。
- 解释行情、技术面和基本面。
- 结合公告、政策及宏观信息分析。
- 提出需要量化验证的新假设。

本轮只改数据获取模块及必要的访问接口。

**禁止修改 `score-1.0.0` 权重、信号判断规则、股票池入选规则或历史效果评价方法。**

现有分析引擎必须继续工作，其输出不应因为本轮数据接口重构而无故改变。

## 四、Phase A2：完善数据完整性与历史数据质量

### A2.1 历史缺口检查

当前系统已能按交易日同步行情，但还需要确认历史缓存是否存在静默缺口。

增加可重复执行的数据检查能力，至少识别：

- 交易日缺少整日行情。
- 部分股票缺少日线。
- 日线与复权因子不匹配。
- 日线与每日指标不匹配。
- 核心指数缺失。
- 同一股票和交易日出现异常或冲突记录。
- OHLC、成交量和成交额明显非法。
- 数据集曾记录成功，但实际缓存已经缺失数据。

区分正常停牌、退市、未上市与真正的数据缺口。

不能仅靠全市场行数比例判断所有数据是否完整。

### A2.2 安全补齐

对于实际缺口，尽量复用已有增量同步能力补齐。

要求：

- 已完整的数据不重复大规模下载。
- 同步失败不会删除旧的完整数据。
- 短返回不能混入已确认完整的快照。
- 成功补齐后更新数据质量状态。
- 补齐前后保留可核验的记录。
- 不允许历史同步改写正式股票池和正式报告。

### A2.3 数据质量语义

保留现有：

- `READY`
- `DEGRADED`
- `NOT_READY`
- `REFRESH_OK`
- `REFRESH_INCOMPLETE`
- `REFRESH_FAILED`

清楚区分缓存质量和最近一次上游刷新结果。

检查 `daily`、`daily_basic`、`adj_factor`、`stk_limit` 和核心指数在不同刷新时点下是否保持一致。

如果不同数据集使用了不同时间获取的缓存，必须能识别并说明。

本轮不要求实现跨所有数据集的全局事务。

## 五、Phase A3：统一数据访问契约

建立供内部分析引擎和 MCP 工具复用的标准化数据访问层。

优先基于当前 SQLite 和 TypeScript 代码实现。

数据访问契约应明确：

- 股票代码格式。
- 交易日期格式。
- 日期区间边界。
- 原始行情与复权行情。
- 成交量和成交额单位。
- 财务指标单位。
- 交易日与自然日区别。
- 数据缺失的表示方式。
- 数据来源与同步时间。
- 查询所允许的最后可用日期。
- 数据质量与错误返回方式。

不要在不同 MCP 工具中分别复制 SQL 查询和复权计算。

### 特别要求：历史可得性

历史查询必须区分：

1. 数据所属交易日或财务报告期。
2. 数据首次发布或实际披露时间。
3. FinanceMCP 获取或更新该数据的时间。

对财务数据，历史查询必须按可靠的公告日期约束。

如果上游 API 没有保存历史修订版本，不能声称实现了严格的 Point-in-Time 财务数据库。

对当前行业分类、历史 ST 状态及其他缺少历史版本的数据，应如实标记限制。

不允许为了补足历史信息而使用未来数据冒充当时已知数据。

## 六、Phase A4：新增结构化 MCP 数据查询

现有五个 MCP 工具继续保留：

- `ashare_data_status`
- `ashare_daily_report`
- `ashare_watchlist`
- `ashare_stock_analysis`
- `ashare_sector_rank`

这些工具已经覆盖预计算研究报告。

本轮优先补充以下**数据访问工具**，不要重复实现分析逻辑。

### A4.1 `ashare_stock_history`

提供指定股票的历史行情。

建议参数：

- `ts_code`
- `start_date`
- `end_date`
- `adjust`：`none`、`qfq`、`hfq`
- `limit`

返回：

- 股票代码。
- 实际日期区间。
- 原始行情和所选复权价格。
- 成交量、成交额。
- 复权方法和价格基准。
- 数据来源。
- 数据质量及缺口提示。

要求：

- 明确不同复权方式的计算公式。
- 不使用查询截止日之后的复权因子。
- 对缺少复权因子的日期明确报错或标记。
- 明确停牌与普通数据缺失。
- 限制查询范围和返回体积。

不得在该工具中重复实现 RSI、MACD 等分析指标。

### A4.2 `ashare_financial_data`

提供股票的财务指标历史。

建议参数：

- `ts_code`
- `as_of_date`
- `start_period`
- `end_period`
- `limit`

返回：

- 报告期。
- 实际公告日期。
- 财务指标及单位。
- 数据来源。
- 记录版本或修订信息（仅在来源支持时提供）。
- 历史可得性说明。

重点验证：

- 不返回 as-of 当时尚未披露的数据。
- 同一报告期多次披露时选择规则明确。
- 空值不转换为 0。
- 财务重述不会无提示地污染历史研究。

如果数据源不具备完整历史修订能力，应明确暴露该限制，而不是构造无法验证的历史快照。

### A4.3 `ashare_market_data`

提供市场级行情和统计数据。

建议支持：

- 指定交易日或日期区间。
- 指定指数集合。
- 受限的数据字段。
- 明确的日期范围和返回数量限制。

优先提供：

- 核心指数 OHLC 与成交额。
- 市场涨跌家数。
- 市场成交额。
- 涨跌停统计。
- 可用股票数量。
- 必要的数据质量信息。

已有计算逻辑可以复用，但不在数据接口中加入新的市场择时规则。

### A4.4 股票基础信息查询

先审阅现有 MCP 是否足以取得股票代码、名称、上市日期、退市日期和行业分类。

如果缺少必要能力，可新增一个受限的股票基础信息查询接口。

不要仅为了数量而新增工具。

注意：当前行业分类不应被当成历史任意日期的真实行业分类。

### A4.5 本轮不实现的接口

`ashare_factor_snapshot` 涉及指标定义、标准化特征和分析规则，应留给下一阶段的独立分析引擎。

本轮只准备其所需的行情、财务和元数据访问能力。

## 七、Phase A5：MCP 查询性能与输出控制

当前 FinanceMCP 运行在 Oracle VPS 上，采用单容器和 SQLite。

保持这一架构。

对新增工具实施：

- 输入参数校验。
- SQL 参数绑定。
- 日期范围限制。
- 最大股票数量限制。
- 最大返回记录数量限制。
- 可预测的排序规则。
- 大结果集的分页或分段查询。
- 清晰的错误信息。

对于 ChatGPT：

- 默认返回研究所需的有限数据。
- 不默认传输全市场多年逐日行情。
- 明确查询边界和数据是否被截断。
- 当数据量超出限制时，要求缩小查询范围或分页。
- 输出应方便后续分析引擎复用，不仅适合人类阅读。

不要新增 Redis、PostgreSQL、消息队列或第二个 HTTP 服务。

性能优化必须由实际查询耗时或扫描量证据驱动。

## 八、Phase A6：验证数据层与分析层隔离

现有分析引擎必须能够继续读取真实数据。

验证：

1. 日频报告正常生成。
2. 股票池数量和成员未因数据访问层重构而意外改变。
3. 指标计算使用统一的复权行情。
4. 正式报告和研究报告仍然隔离。
5. MCP 新工具没有写数据库的权限。
6. 历史查询不会写入正式股票池。
7. 数据查询不触发分析引擎自动调参。
8. 现有五个 MCP 工具全部回归通过。

允许修改分析模块中调用数据访问函数的少量代码，以保持接口一致。

禁止改变指标公式、评分规则和选股行为。

## 九、Phase A7：测试与真实数据验证

必须同时覆盖确定性单元测试、SQLite 集成测试和真实缓存副本测试。

### 必测情形

- 正常交易日行情。
- 非交易日查询。
- 停牌股票。
- 新上市股票。
- 已退市股票。
- 缺少复权因子。
- 股价除权除息。
- 财务公告日晚于查询 as-of。
- 财务报告期与实际公告日期不同。
- 上游短返回。
- 上游 API 错误。
- 历史缓存缺口。
- 数据源修订。
- 超范围查询。
- 空结果。
- MCP 只读访问。
- 同一查询重复执行结果一致。
- 完整旧版接口回归。

对历史可得性和复权计算，应使用专门构造的反例，而不只测试真实数据上的正常路径。

### 真实数据验证

使用生产数据库副本。

基于截至 2026-10-16 的现有历史数据，选取：

- 一只长期上市的大市值股票。
- 一只近期上市股票。
- 一只历史停牌或退市股票。
- 一只发生过除权除息的股票。
- 一只存在多期财报记录的股票。
- 核心宽基指数。

验证其查询字段、日期、复权结果和财务披露约束。

通过后再对部署的 MCP 进行只读端到端检查。

不允许在生产数据库直接执行破坏性测试。

## 十一、执行方式和交付要求

以 `ashare-v1-fix2` 为代码基线创建新的工作分支，例如：

`feat/ashare-data-service-v1`

按依赖顺序连续完成全部工作。不要在每个小阶段结束后等待用户确认。

完成后：

1. 执行完整构建。
2. 执行全部自动化测试。
3. 执行真实缓存副本验证。
4. 执行已有 MCP 回归测试。
5. 对生产部署执行安全检查。
6. 如果所有验收条件满足，备份正式数据并部署新增只读数据工具。
7. 核验部署后旧工具仍正常工作。
8. 提交并推送工作分支。
9. 提供 commit SHA 和完整验收摘要。

如果某项检查失败，先定位并修复真实缺陷。不要通过放宽测试断言使其通过。

如果生产部署存在数据损坏风险，应保留已验证的代码成果，并明确说明未部署的原因。

不要修改其他定时任务，也不要触发尚未到日期的连续三日验收。

## 十二、成功判据

本轮完成时，应满足以下条件：

- FinanceMCP 的数据获取模块可以独立提供 A 股历史行情、财务历史和市场数据。
- 内部量化引擎和 MCP 使用一致的数据定义。
- 数据缺失、更新失败及历史时间限制有明确表示。
- ChatGPT 能通过 MCP 按需查询结构化真实数据，而不必依赖预先生成的股票池报告。
- 正式量化分析结果和原有五个 MCP 工具保持稳定。
- 新增接口通过自动化测试和真实缓存验证。
- 当前部署架构没有增加不必要的服务或基础设施。
- 后续量化分析引擎可以在明确的数据契约上独立迭代。

**本轮结束后停止开发，不进入评分、信号、回测或股票池策略优化阶段。**

最终使用中文报告：实现内容、测试证据、部署状态、未解决问题，以及下一阶段分析引擎可以直接使用的数据能力。
